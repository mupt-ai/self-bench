SelfBench turns merged pull requests into Harbor tasks. This page covers the pipeline, the rules an accepted task must meet, and what an export contains.

## Terms

- A **candidate** is one source pull request being turned into a task.
- The **base snapshot** is the repository state before the change.
- The **reference patch** (gold) is the PR's non-test implementation.
- The **held-out test patch** is grader code hidden from evaluated agents.
- A **fail-to-pass** test fails on the base snapshot and passes after a correct implementation; a **pass-to-pass** test already passes and guards existing behavior.
- Harbor's **nop** run applies no solution; its **oracle** run applies the reference patch.

## Pipeline

A batch is one `selfBenchBatchWorkflow` (`src/generation/batches/`), with each discovery shard and each candidate as its child workflow, the same shape as an evaluation. The batch writes its own Postgres record (the plan and its phase); each candidate workflow writes its task's row as it goes, and settles it with its verdict however it ends, cancelled or out of time included. The pages only read those rows; a running child's current attempt and sandbox cost are read from Temporal. Cancelling the batch cancels every child and waits for each to stop.

1. **Provenance.** The API pins the default branch's head; the batch workflow then lists up to 500 merged PRs with the submitter's GitHub token. Each PR from a non-bot author that clears the size gate becomes a provenance record: its exact title and body, with common credential forms redacted. No model writes request text.
2. **Discovery.** PRs are split into shards, each one `selfBenchDiscoveryShardWorkflow`. Each shard sees a pool of about 1.5× the requested count in PRs (at least 25) and proposes up to its share of each tier's count. Candidates are deduplicated by source PR.
3. **Authoring and review.** Every candidate runs as one `selfBenchAuthorWorkflow`. Nothing is backfilled: a rejected candidate is a rejection in the batch status, and a batch can accept more tasks than it asked for.
4. **Export.** Once every candidate settles, accepted tasks are packed into the batch export.

**Add PRs** skips discovery and authors each chosen PR as its own candidate.

Agents run in fresh sandboxes (Docker locally; Modal, Vercel, or E2B hosted) built from `Dockerfile.sandbox`. A sandbox reports back to the API over signed callbacks (`/api/sandbox/*`) rather than holding a worker connection, and uploads everything it produces under `runs/<runId>/…` in the artifact store. Harbor gates and solver trials run on a separate `<task queue>-harbor` queue, which the GKE workers serve in production.

Evaluations from the **Run** page are one `selfBenchEvaluationRunWorkflow` per model, with one child `selfBenchSolverTrialWorkflow` per task and harness. Each trial is one Harbor run with only the selected credentials.

## Authoring and verification

One authoring agent session owns the whole task, written as plain files in `/work/task/`: `instruction.md`, `gold.patch`, `test.patch`, a `Dockerfile` that unpacks the base snapshot into `/app` and prepares it, a `smoke.sh` that proves the environment is ready for the agent, a `run-tests.sh` that runs the `fail-to-pass` or `pass-to-pass` tests, and, when the tests need a service, a `services.sh` that starts it. The task's repository, base commit, and pull request are the candidate's, and every task gets the same limits. The agent then calls `verify`.

`verify` runs a static check in the sandbox (the files, patch path safety, the audit, and both patches applied to the base commit) and returns failures immediately. Otherwise it ends the turn, and the worker compiles the task, builds its images, and runs the Harbor gates on them:

1. **build**: the agent image (from `environment/`) and the separate verifier image (from `tests/`), both the author's Dockerfile followed by SelfBench's own steps, build; a failing step of the author's is theirs to fix, with the build's log in the report;
2. **smoke**: `smoke.sh` succeeds as the agent (agent image, user, and network allowlist);
3. **nop**: the new tests fail on the base snapshot and the regression tests pass;
4. **oracle**: the reference patch applies and every selected test passes;
5. **determinism**: the fail-to-pass tests pass a second time with the oracle.

The next turn resumes the same session in a fresh sandbox with the report as its next message. A round allows five `verify` calls and ends with `submit_task`. A fresh read-only review agent then judges each green submission: accept, reject, or send suggestions back for another authoring round. Three failed rounds reject the candidate; a step that still fails after its retries (a Harbor check gets four attempts) marks it `infrastructure_failed`.

The authoring prompt, including the anti-coupling rules, is [`src/generation/pipeline/prompts/authoring.md`](https://github.com/mupt-ai/self-bench/blob/main/src/generation/pipeline/prompts/authoring.md).

## What an accepted task must satisfy

| Difficulty | Reference patch |
| --- | --- |
| easy | 20+ changed lines across 1 implementation path |
| medium | 50+ changed lines across 2 implementation paths |
| hard | 100+ changed lines across 3 implementation paths |

A task takes the hardest tier its reference patch reaches, up to the candidate's. Every task also needs a held-out test patch that shares no files with the reference patch, deterministic repository-native setup and tests, green smoke/nop/oracle gates, and the reviewer's acceptance.

- **Instruction.** It may restate the PR's request but may not add behavior inferred only from the implementation or tests.
- **No test-to-gold coupling.** Held-out tests exercise a public API, command, persistence boundary, or extension seam. They may not import the gold's private helpers or pin internal SQL, query counts, private schemas, telemetry layout, incidental error wording, or UI composition unless the request makes that public.
- **Environment.** The agent derives runtime, dependencies, fixtures, and services from the pinned commit's CI, Dockerfiles, devcontainer, and lockfiles, and installs all of them in its Dockerfile, including what the reference patch adds. Services the tests need, such as a database, run inside the image: an optional `services.sh` starts them as root before the agent's patch is applied, and the agent's image carries it too, so the agent can start them while it works. The agent names base images by tag, or by a digest the repository itself pins; the trusted compiler pins each `FROM` tag to the digest its registry serves and rejects a reference the registry does not serve. The compiler rejects files that reference secret material.

## What the evaluated agent sees

The agent gets the base snapshot, the instruction, and the task's environment. It never sees the held-out tests or the reference solution; Harbor mounts `solution/` only for the oracle.

The agent runs as `root` in `/app` as the Dockerfile left it, with network limited to the host its model is reached at: SelfBench's model gateway, which holds the credential and gives the agent only a key for its one model (Dari's router and Muse Code reach their provider directly). Its diff is taken against the post-setup snapshot. The verifier refuses the patch unless its recorded base tree matches the verifier's own `HEAD`, then applies it to a clean copy without the files the held-out tests touch, and restores those files, so tampering can only produce a tree the agent could have written directly. Existing tests that `run-tests.sh pass-to-pass` runs are not held out: they run as the agent left them.

## Export

A batch export is a `.tar.gz`, downloaded with `GET /v1/runs/:runId/export` (see the [Workspace API](/api-reference/workspace)):

```text
manifest.json
tasks/
└── TASK_ID.tar.gz
    └── harbor-task/
        ├── instruction.md
        ├── task.toml
        ├── environment/
        │   └── Dockerfile
        ├── tests/
        │   ├── Dockerfile
        │   ├── test.sh
        │   └── test.patch
        └── solution/
            ├── solve.sh
            └── gold.patch
```

`manifest.json` pins the source commit, SelfBench build, generation backend, Harbor environment, task IDs, and archive SHA-256s. The export keeps the first accepted task per source PR and lists the rest under `droppedDuplicates`.

When the deployment builds task images (`SELFBENCH_TASK_IMAGE_REPOSITORY` and `SELFBENCH_TASK_IMAGE_BUILDER`), every check builds the compiled task's two images before its gates, and the gates run on exactly those digests on the run's sandbox provider. Hosted SelfBench builds on Google Cloud Build in its own GCP project, for every run, whichever sandbox account the run uses: the build is SelfBench's, the gates and trials are the run's. A build runs the author's Dockerfile and code from the repository under test, so it runs as a service account of its own that may only push task images, write its layer cache and logs, and read SelfBench's Docker Hub mirror; it never holds the worker's credentials. The worker uploads only the two small build contexts; the build fetches them and the repository snapshot through short-lived signed links and checks their digests before any task code runs. Each candidate keeps a layer cache, so its later checks rebuild only what changed. A local stack can build with its own Docker instead (`SELFBENCH_TASK_IMAGE_BUILDER=docker`, the `images` Compose profile); without a builder, Harbor builds the task's Dockerfiles itself, as it always has.

A task the pipeline accepts settles with its images, no human approval needed, and publishes its execution bundle: the delivered execution tree. Each Dockerfile is a `FROM` of its image's immutable digest. The repository checkout, dependencies, setup, smoke script, and verifier runtime are already in those images; no repository archives, `run-tests.sh`, or compiler manifest are duplicated in the execution bundle. Tasks compiled before authors wrote their own Dockerfiles may declare services; they also retain their `docker-compose.yaml` files, whose `main` service starts from the verifier image, and E2B does not run them. If the execution bundle cannot be published, the candidate fails as an infrastructure failure rather than run without its images.

When a candidate finishes, every image it built except its accepted pair is deleted. When a person rejects or deletes a task, its images are deleted and it returns to its full build bundle, unless a saved comparison, a release, or another task still names them. A kept task without images (accepted before images were built, or approved again after a rejection removed them) is rebuilt when a person reviews it, or by the operator's backfill: its compiled task is built and checked again on its own run's provider and account, and only images that pass every gate are recorded.

The authored files and full build bundle remain separate, immutable provenance artifacts; reviewers inspect the full source tree. Docker trials pull a task's images directly; Modal, E2B, Daytona, and Vercel trials receive short-lived pull grants for only the task's image pair through the API; Daytona's temporary registry configuration is removed after the sandbox starts. Vercel is not a selectable evaluation sandbox.

Existing tasks, saved comparisons, and releases keep their original bundle references.

`task.toml` owns execution configuration and retains separate-verifier isolation. Harbor collects the agent's patch at runtime, then `tests/test.sh` applies it and the hidden test patch to the clean verifier checkout. The agent image contains neither hidden tests nor the reference solution. Only the verifier image contains grader code; Harbor supplies `solution/` to oracle runs.

Exports include hidden tests and reference solutions, unencrypted. Keep them private. Image-backed exports require access to their registry: the SelfBench app uses scoped pull grants for supported providers, while a standalone Harbor run needs registry authentication. They are native Harbor tasks, not self-contained image backups. For example, after authenticating Docker to the image registry:

```bash
harbor run --path ./harbor-task --agent codex --model gpt-6-sol --env docker
```

### Delivering Tasks to Customers

A customer who runs tasks themselves pulls the images through the API's registry with a grant of their own, never with access to the whole repository. The operator issues one with the API token:

```bash
self-bench grant create --label "Acme" --task 412 --task 418 --days 30 --with-verifier
```

The response holds a registry login (the API's host, the user `selfbench`, and a password shown only once) and the image references the grant reaches. A grant reaches only accepted tasks with exported images, and only those tasks' images. It includes the verifier images, which hold the tests, only with `--with-verifier`; without them a customer can run agents but not grade them. `self-bench grant list` shows every grant, and `self-bench grant revoke GRANT_ID` cuts one off at its next request. Copies a customer has already pulled stay with them.

The task's Dockerfiles name the images in SelfBench's Artifact Registry repository, which the customer cannot reach, so point them at the API's registry before running:

```bash
docker login api.selfbench.dev -u selfbench   # the grant's password
grep -rl --include=Dockerfile '<region>-docker.pkg.dev/<project>/selfbench-tasks/' ./harbor-task \
  | xargs sed -i 's#<region>-docker.pkg.dev/<project>/selfbench-tasks/#api.selfbench.dev/#'
harbor run --path ./harbor-task --agent codex --model gpt-6-sol --env docker
```

The digests stay the same, so the customer runs exactly the images that passed verification.
