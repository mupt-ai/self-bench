Once a comparison finishes, work from the overall scores down to single tasks.

## Scores

**Results** in the app, `self-bench results`, or [`GET …/evaluations/results`](/api-reference/results) show each configuration (model, reasoning, harness) with its pass rate and cost per task. Results count each configuration's latest scored result on each accepted task, the same results a release publishes. The Pareto frontier in the app marks the settings no other setting beats on both accuracy and cost.

## One Task

Tasks that most configurations fail tell you the most, about the models or about the task itself. Results list tasks hardest first.

```bash
self-bench task results BATCH TASK --repo acme/app
```

This shows every configuration's result on the task, why each failure failed once explained, and the task's fairness verdict once audited.

- **Explain failures.** `self-bench task explain BATCH TASK --repo acme/app --wait`, or **Explain Failure** on a trial, has a model read the trial's transcript and test output and say why it failed.
- **Audit fairness.** `self-bench task audit BATCH TASK --repo acme/app --model M --credential KEY --wait`, or **Audit Task**, has a model read the task and its failed attempts and judge whether the failures are the agents' or the task's: `fair`, `unfair`, or `unclear`.

When a task is unfair, [revise it](/guides/author-scenarios#edit-a-task) with the audit as feedback, or reject it. Rejected tasks drop out of results and releases.

## Compare Models

**Model Summaries**, or `self-bench summaries create --repo acme/app --model M --credential KEY --wait`, writes one report: what the configurations share, then where each succeeds and fails. You can publish it with a [release](/guides/publish-results).

Audits and summaries run on a saved model API key, which you choose. Explanations also run on the deployment's managed model where it offers one. Each sends the task's files and the trials' output to that model.
