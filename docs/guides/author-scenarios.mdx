A scenario task starts from a description instead of a merged PR. You describe a situation an agent should handle, ideally one it got wrong, and attach any real files from it. The authoring agent writes the files the evaluated agent starts with, the instruction, hidden tests that check the outcome, and a reference outcome. The same gates and independent review that check PR tasks check scenario tasks.

For example: *"My rec league schedule is a spreadsheet that says I'm on team 6. Last week an email said I was traded to team 3. Asked when my next game is, my agent answered from the spreadsheet."* The author builds a workspace with the spreadsheet, a mailbox holding the trade among unrelated mail, and an instruction such as "When is my next game? Write `/app/answer.json`". The tests pass only for team 3's next game.

## What a Scenario Task Is

| | PR task | Scenario task |
| --- | --- | --- |
| Starting files (`/app`) | The repository at the PR's base commit | The `workspace/` the author writes |
| Reference solution | The PR's implementation | The outcome a careful agent leaves, such as an answer file |
| Difficulty | From the size of the change | The tier you choose |
| Graded by | Hidden tests | Hidden tests |

Scenario tasks belong to a connected repository like any other task, so you approve them, evaluate them, and release them the same way. Nothing is read from the repository or GitHub. The tests read only what the agent leaves in `/app`, so a good scenario names an output the tests can check: a file to write, or files to change.

## From the App

On a repository, choose **Add Scenario**. Give it a title and a description, choose a difficulty, attach any files (up to 20 files and 20 MB in all), then configure generation as for **Add PRs**. The task appears in the dataset in progress.

## From the CLI or API

The `self-bench` CLI and the [Workspace API](/api-reference/workspace) act as the owner of a personal API key. Create a `write` key under **Settings → API Keys**:

```bash
export SELFBENCH_API_URL=https://app.selfbench.dev
export SELFBENCH_API_KEY=sbk_…

self-bench scenario create --repo mupt-ai/self-bench \
  --title "Traded to a New Team" \
  --scenario-file scenario.md \
  --attach schedule.xlsx --attach trade.eml \
  --difficulty medium
```

`--org` names the workspace when it isn't the repository's owner. Generation defaults to managed models and sandbox, as in the app; `--model`, `--reasoning`, `--model-credential`, `--sandbox`, and `--sandbox-credential` change it, or `--generation @settings.json` gives the full settings. See [Create a Scenario Task](/api-reference/create-scenario) for the HTTP request.

## Edit a Task

Every task, scenario or PR, can be revised. A revision is a new task whose agent starts from the task's last draft, addresses your feedback, verifies the result, and goes through review again. The original task and its evaluations stay as they are.

To edit the files yourself, pull the draft, change it, and send it back with your feedback:

```bash
self-bench tasks --repo mupt-ai/self-bench
self-bench task pull RUN_ID TASK_ID ./traded --repo mupt-ai/self-bench
# edit ./traded/instruction.md, ./traded/workspace/…, the patches, or the scripts
self-bench task revise RUN_ID TASK_ID --repo mupt-ai/self-bench \
  --draft ./traded --feedback "Ask for the venue as well as the time."
```

The agent keeps your edits, fixes what the checks report, and submits. `task approve`, `task reject`, `task cancel`, and `task delete` do the rest of the review from the CLI.

## Write a Good Scenario

- **Name the mistake.** Say what the agent did wrong and what a careful person would do instead. The task is built to reward exactly that.
- **Say where the truth was.** "A later email superseded the spreadsheet" tells the author what the workspace needs.
- **Attach the real files** where you can. The author keeps the details the scenario depends on and replaces the rest with fictional ones.
- **Make variants.** One scenario is one data point. Separate tasks for a trade, a rescheduled game, and two emails that contradict each other measure the capability better than one.
