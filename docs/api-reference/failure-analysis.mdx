Each of these sends your results and task files to a model, runs in the background, and answers `202`. Name the model with a saved model API key and a model ID, as `{ "credentialId": "<uuid>", "model": "gpt-6.1-sol" }`. Poll the route's `GET` until `running` is `false`.

## Failure Explanations

Why one trial failed its tests, in plain language.

| Method | Route | Body or query | Returns |
| --- | --- | --- | --- |
| `GET` | `{scope}/evaluations/{evaluationId}/explain` | `?runId=…&taskId=…&harness=…` | `{ available, running, reason? }` |
| `POST` | `{scope}/evaluations/{evaluationId}/explain` | `{ runId, taskId, harness, explanation? }` | `202` |

`explanation` is the model to use. Leave it out to use the deployment's managed model, where it offers one. Only a trial that failed its tests and has no explanation yet can be explained (`409` otherwise). An attempt that ended without an answer can be retried after 10 minutes (`429` until then).

The explanation appears as the trial's `failureSummary` in [Results](/api-reference/results) and in `GET {scope}/evaluations/{evaluationId}`. Each failed result in Results names the `evaluationId` and `harness` this route takes.

## Task Audits

Whether a task is fair: a model reads its instruction, tests, and up to 12 failed attempts, and judges whether the failures are the agents' fault or the task's.

| Method | Route | Body or query | Returns |
| --- | --- | --- | --- |
| `GET` | `{scope}/evaluations/audit` | `?runId=…&taskId=…` | `{ available, running, audit?, failure? }` |
| `POST` | `{scope}/evaluations/audit` | `{ runId, taskId, audit }` | `202` |

`audit` is required. A task with no failed attempt has nothing to audit (`409`).

```json
{
  "audit": {
    "verdict": "unfair",
    "text": "Every failure writes the right output; the tests also require a log line the instruction never mentions.",
    "model": "gpt-6.1-sol",
    "attempts": 6,
    "failures": 6,
    "auditedAt": "2026-11-06T12:00:00.000Z"
  }
}
```

`verdict` is `fair`, `unfair`, or `unclear`. For an unfair task, [revise it](/api-reference/tasks#revise-a-task) with the audit as feedback, or reject it.

## Model Summaries

One report comparing configurations: an overview, then what each one does well and where it fails.

| Method | Route | Body | Returns |
| --- | --- | --- | --- |
| `GET` | `{scope}/evaluations/summaries` | | `{ available, running, report?, failure? }` |
| `POST` | `{scope}/evaluations/summaries` | `{ configurations, summary }` | `202` with the configurations it will summarize |

`configurations` are up to 12 setting keys from [Results](/api-reference/results); keys with no scored result are dropped. `summary` is required. One report runs at a time per scope (`409` while one is running). A report can be published with a [release](/api-reference/publish-release).

```json
{
  "report": {
    "overview": "Both configurations pass the small fixes; they part on multi-file changes…",
    "summaries": [{ "configuration": "[\"gpt-6.1-sol\",\"pi\",\"high\"]", "text": "…", "tasks": 24, "passed": 17 }],
    "model": "gpt-6.1-sol",
    "summarizedAt": "2026-11-06T12:00:00.000Z"
  }
}
```

All three run under a repository, [benchmark, or group](/api-reference/create-benchmark) scope.
