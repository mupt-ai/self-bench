---
title: "API Keys"
description: "Authenticate requests to the private workspace API."
icon: "key"
---

Create keys in **Settings → API Keys**. The secret is shown once. The [CLI](/cli/overview) reads it from `SELFBENCH_API_KEY`. Use `Authorization: Bearer $SELFBENCH_API_KEY` or `X-API-Key: $SELFBENCH_API_KEY`.

| Scope | Access |
| --- | --- |
| `read` | GET requests only |
| `write` | Actions allowed by the key owner's workspace role |

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/api/me` | Caller, workspaces, auth method, and managed-offering status |
| `GET` | `/api/api-keys` | Active keys without secrets |
| `POST` | `/api/api-keys` | Create a key with `{ "name": "CI", "scope": "read" }` |
| `DELETE` | `/api/api-keys/{id}` | Revoke a key |

Creating and revoking keys requires a signed-in browser session; a key cannot mint another key, but it can revoke itself. `self-bench login` creates a key through the browser: the app asks you to approve the CLI, then hands it a one-time code that only that CLI can exchange (OAuth with PKCE, at `/auth/cli` and `/auth/cli/token`). API-key requests do not need an `Origin` header.
