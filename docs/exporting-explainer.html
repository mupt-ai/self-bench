Production Batch · What “Exporting” Means

The work finished. The package didn’t.

A batch has two different kinds of work: generate and verify candidate tasks, then package the successful tasks into a downloadable archive. “Exporting” is that second step—not proof that generation is still running.

02AuthorTemporal workflows generate and verify each candidate.
03ExportingCollect accepted tasks and build one archive.
04CompleteSave the archive reference to the batch record.

What the code does

  1. When every candidate is settled, advanceBatch changes the durable batch phase to exporting.
  2. The API’s batch reconciler starts or observes a stable-ID Temporal export workflow and persists its artifact reference when complete.
  3. A Temporal worker runs export: it reads task definitions and bundles from artifact storage, starts an export sandbox, and asks it to make export.tar.gz.
  4. The worker stores the archive in artifact storage and returns only the small artifact reference through Temporal. The API records it and changes the phase to complete.

Relevant code: src/generation/batches/advance.ts, service.ts, src/generation/batches/temporal.ts, and src/generation/pipeline/workflows.ts.

What changed: the API still coordinates durable batch state, but export execution and archive data transfer now happen in the Temporal worker. The API handles only workflow metadata and the resulting artifact reference, not bundle or archive bytes.

What production evidence says

Logs for batch-cd664ae6-006d-4065-ae5d-d08db435ddb1 show repeated messages saying export failed and would be retried. Production Cloud Run logs also show the API exceeding its 2 GiB memory limit and instances restarting.

Most likely explanation: the API is being killed or failing while it handles the export, before it can save the reference and mark the batch complete. The current error handler suppresses the actual exception, so logs do not prove exactly which export operation fails. This is strong evidence, not a confirmed root cause.

Those historical memory-limit events are consistent with the previous design, where API export retries performed the data-heavy work. The underlying exception was suppressed, so logs alone did not prove memory exhaustion was the specific export failure.

Does Kubernetes fix it?

The API memory fix

Export now runs on the existing Temporal worker, which has a larger memory allocation. GKE’s Harbor workers are a separate pool; they are not what moves this export.

Still worth monitoring

The worker still handles artifact bytes, so very large exports can use worker memory. If that becomes a problem, stream artifact reads and writes rather than buffering whole archives.

In one sentence

“Exporting” means the system has not yet successfully packaged, stored, and recorded the batch result. The API now dispatches this work to a Temporal worker, keeping the memory-intensive transfer off Cloud Run.
